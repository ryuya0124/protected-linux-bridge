# Bridge内でのDebian導入

「VM」→「Debianを準備」から、標準ターミナルのインストーラーを開かずに導入できます。

1. 既存の作業を保存し、VMと起動支援を停止します。
2. **Debianをダウンロードして導入**を選びます。既に標準ターミナルで同一イメージを導入済みなら、**既存の標準イメージを取り込む**も選べます。
3. rootを許可し、完了まで画面を開いておきます。
4. 「概要」で接続を有効にし、**Debianターミナル**を開きます。新しいタブごとに独立したゲストのシェルへ接続します。最大8タブです。
5. GUIが必要な場合、そのターミナル内で`plb-install-gui`を実行し、Bridgeから「全画面で開く」を使います。Linux側の追加パッケージ導入には通信と時間が必要です。

この経路にはVectorや標準ターミナルの画面操作は不要です。対応するVirtualization APEXと標準ターミナルAPK自体は、ROMの互換性検証の一部として引き続き必要です。標準ターミナルから接続したい場合にだけ、Vectorで適用先を`com.android.virtualization.terminal`にします。

インストールで既存のVMディスクを上書きしません。既にBridgeの導入イメージがある場合も拒否します。既存のVMベースがキャッシュ済みならそのまま使い、新しいダウンロードで書き換えません。

## 容量と配布元

Googleの`dl.google.com/android/ferrochrome/5100000/aarch64/images.tar.gz`を使います。現在の固定カタログは**ARM64 Debian 13.7 / trixie**です。

- ダウンロード：607,391,791 bytes（約580 MiB）。アプリの通信権限でHTTPS取得し、rootプロセスにはストリームだけを渡します。
- 導入イメージ：3,085,959,168 bytes。初回起動では、これとは別に読み取り専用ベースと専用QCOW2を作成します。7 GiB以上の空きを推奨します。
- 展開前アーカイブと展開後root_partの両方を固定SHA-256で検証します。配布元で同じURLの内容が変わっても、自動的に受け入れません。
- 展開するのは`root_part`だけです。アーカイブ内の`vmlinuz`や`initrd.img`はインストール・実行しません。ホストカーネルには触れません。
- イメージはAPK／GitHubへ再配布せず、アプリから元の配布元へ取得します。[カタログ・ハッシュ](../compatibility/debian-image-5100000.json)を参照してください。

配布先の根拠は、対象ROMのTerminal 37の`ImageArchive`実装と、[AOSPのImageArchive](https://android.googlesource.com/platform/packages/modules/Virtualization/+/dd12ec774f09365d4f898c7739b23356e35198cc/android/TerminalApp/java/com/android/virtualization/terminal/ImageArchive.kt)です。後者は関連する公開設計の参照であり、対象ROMと同一コミットであるとは主張しません。

## 保護境界

固定した通常ファイルだけのTAR形式を受け入れます。アーカイブ中のパスを展開先として使わず、リンクや未知のエントリー・サイズ・ハッシュ変更を拒否します。失敗したイメージは一時領域にとどまり、検証後、アプリからの確定要求を受けてからフォルダを昇格します。転送の終了だけで自動的に確定しません。

Bridgeのターミナルが送るのは、認証したroot管理プロセスへのゲストPTY要求です。入力をホストのrootシェルへ渡す機能はありません。WebViewは同梱HTML／xtermだけを表示し、ファイル・外部コンテンツ・ネットワーク読込を無効にします。閉じたタブの出力待ちや接続を解放します。タブを閉じるとゲストの対話セッションが終了し、VMのkeep-alive／寿命は設定に従います。

## 現在の検証範囲

固定アーカイブを実際にホストJavaの同じ導入コーデックへストリームで渡し、約3 GBの完全展開・ハッシュ照合が成功しました。Macにアーカイブ全体は保存せず、展開試験後のイメージは削除しました。Windows/WSLで`debugfs`による読み取り専用のファイル抽出から`dpkg`のELF64 ARM64とDebian 13.7を確認しています。

Android 17 Galaxyでは512 MiBの保護CPU VMと、既存Debianイメージの読み取り専用マウント・`dpkg --print-architecture`のarm64結果を確認しました。これは新しい導入画面・複数タブ・書き込み可能な通常セッション・GUIの実機検証とは別です。ユーザーによるホストのソフトリブート後は一度接続を停止し、再開許可後に非GUIの確認だけを再開しました。

新しい画面と初回導入・復元は実機未検証です。AndroidゲストとVulkanは引き続き無効です。

## 標準インストール画面がすぐ閉じる場合

標準ターミナルは導入完了マーカーがあると、インストーラーを正常終了します。
Android 17実機のイベントログでも `app-request` による終了を確認しており、この操作の
プロセスクラッシュは記録されていません。Bridge 0.5.0-alpha.4以降は起動前に導入状態を
調べ、導入済みなら説明と「標準ターミナルを開く」「BridgeのDebian導入」を表示します。
既存イメージや完了マーカーを削除して画面を開かせる処理は行いません。

未導入時は標準インストーラーを開き、ActivityManagerの起動確認を要求します。
root側が成功コードだけを返した場合は成功としません。状態判定の単体テストと実機の
既存マーカー／終了記録は確認済みです。修正後のダイアログと未導入端末での画面操作は
GUI操作を行わない検証範囲のため、実機未確認です。
